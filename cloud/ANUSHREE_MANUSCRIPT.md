## 6.3(A) Cloud provisioning and operational dashboard

The cloud layer uses the ThingsBoard EU Cloud tenant at `https://eu.thingsboard.cloud` to manage three virtual water-source devices and present telemetry to a municipal duty officer. The browser footer identified the platform as v4.4.1PAAS-EU. The implemented edge process assigns a separate MQTT client and access token to each source, publishes to `v1/devices/me/telemetry` over TLS on port 8883, and attaches the original Unix epoch millisecond timestamp to each measurement. The three devices are named `node-a`, `node-b`, and `node-c`, at (27.7172° N, 85.3240° E), (27.6790° N, 85.3190° E), and (27.7500° N, 85.3700° E), respectively. All three were assigned the `Post-Flood Water Source` profile and have separate access tokens kept in the ignored local `.env`.

The normal inactivity target in the Task 2 design is 180 min; the event/burst target is 45 min. In the CE version used here, device inactivity is controlled by a platform default or the per-device server-side `inactivityTimeout` attribute in milliseconds [TB-CONNECT]. Accordingly, the normal override is 10,800,000 ms and the burst override is 2,700,000 ms on each of the three devices. Switching between these values requires an explicit mode change; the profile itself does not automatically make this switch. This cloud-side activity detection is separate from the edge simulator's 90 s `node_inactive` demonstration flag. For a 15 min demonstration, [STATE WHETHER A SHORTENED DEMO TIMEOUT WAS USED AND HOW THE PRODUCTION VALUES WERE RESTORED]. The `lastActivityTime` and `active` attributes are displayed alongside the last reported water measurements so historical replay is not mistaken for current connectivity.

The dashboard has a fleet state and an individual-source state. Its opening view places a status table and an OpenStreetMap-backed map at the top. The table identifies each device by name, severity, last server activity and local queue depth; the map locates the same devices and uses a severity-dependent marker color. The edge publishes `severity` as `Normal`, `Warning`, `Major`, `Critical`, or `Fault`, so a color change can be driven directly by the telemetry stream. Labels repeat the severity in text to avoid relying on color alone. A click on a map marker or status row opens a detail state for that device through a ThingsBoard entity alias [TB-DASH, TB-ALIAS]. This layout is intended to answer the first operational question, “Which source needs attention now?”, before the officer inspects detailed measurements.

The detail state contains radial gauges for pH and turbidity, a digital TDS gauge, two history plots, and an alarms table. The pH gauge marks values below 6.5 and above 8.5 in red. The turbidity gauge marks 5, 50 and 200 NTU, while the TDS gauge is configured with fixed color ranges at 500 and 1000 ppm; its corrected appearance needs browser confirmation. One trend displays turbidity, pH and TDS with distinct units and independent scales; the second displays temperature and flow with separate axes. The charts cover the demonstration's complete time window and retain acquisition timestamps from the edge payload, which is necessary to display buffered measurements at the time they were observed. The alarms table shows server-side alarm creation and clearance. Those rules are configured and evaluated separately by the alarm-rule workstream; the dashboard does not infer a server alarm solely from a colored marker.

The node table exposes `buffer_depth` as “Queue at sample.” This value is included in each edge telemetry payload and indicates queued rows at the time of that sample; it is not a live count of unsent rows. During a complete disconnection, the cloud cannot see the continuously growing local depth until connectivity returns. The live terminal and SQLite database are therefore the evidence for accumulation during the outage; the backfilled `buffer_depth` samples provide a retrospective cloud trace. RSSI is shown as “N/A” because the three virtual nodes contain no radio model. A fabricated signal-strength trace would imply a measurement that this prototype does not make. The dashboard avoids a “safe to drink” label because pH, turbidity and TDS do not establish microbiological safety.

The dashboard was saved to the tenant and read back through its API as `cloud/exports/post-flood-dashboard.json`. This JSON preserves the layout, widgets, aliases and navigation but does not contain live time-series data. The redacted `cloud/exports/post-flood-device-profile-api.json` is an API snapshot; profile UI export and dashboard re-import have not been checked. The first fleet screenshot confirms three markers, gauges and trends render. The detail screenshot shows pH 6.33, turbidity 521.1 NTU and TDS about 421 ppm, matching the `node-b` telemetry at capture time and confirming the selected-source binding. After setting OpenStreetMap as the first layer and correcting the alarm filter, the refreshed fleet screenshot confirms map tiles load and the “Failed to parse the payload” banner is gone. ## 7.1 Tool justification

Python 3.10+ was selected for the virtual edge implementation because the assignment requires a scripted ESP32-S3 surrogate and Python provides deterministic scenario control, documented numerical processing and direct integration with `sqlite3` and `paho-mqtt`. It lets the group demonstrate the complete data path and outage behavior without claiming to have deployed physical hardware. The edge implementation uses SQLite with Write-Ahead Logging to persist each sample before the publish attempt. This ordering is central to the store-and-forward requirement: an interrupted network cannot erase a reading that has already been committed locally. MQTT QoS 1 over TLS on port 8883 provides an authenticated and encrypted publish path; the publisher waits for a PUBACK before marking a row synced. QoS 1 may redeliver a message after an ambiguous failure, so cloud verification should compare timestamps and device identifiers rather than assume that every publish attempt creates one unique observation.

ThingsBoard was chosen for the cloud layer because one platform supplies device identities, access-token authentication, time-series ingestion, device activity state, configurable dashboards, maps and alarms [TB-PROFILE, TB-DASH]. This matches the small three-node prototype and gives the duty officer an operational view without building a separate web application. The deployment tested here was the EU Cloud service, whereas the Task 3 brief names self-hosted CE or `demo.thingsboard.io`. The team must confirm that the EU Cloud tenant is acceptable for assessment or move the configuration to an allowed tenant before submission. A self-hosted CE deployment would require the municipality to operate backups, updates, TLS certificates, access control and service monitoring.

A production ESP32-S3 implementation would replace Python's simulation and threads with firmware tasks, hardware sensor acquisition, field calibration and an embedded persistent store. The firmware would need an outage-safe write protocol, bounded flash wear, a reliable clock source for preserved acquisition timestamps, certificate rotation and a documented policy for queue exhaustion. Those changes are substantial and cannot be inferred from successful simulator results. The selected tools are appropriate for validating the proposed data flow and operator interface, while the hardware and field-safety claims remain outside this software prototype.

## 8.1 Data visualisation

After the scripted intrusion command, the stored `node-a` reading at 11:51:11 NPT showed turbidity 341.4 NTU, TDS 346.24 ppm and pH 6.40, with `Critical` severity. Relative to its 11:50:31 baseline, turbidity and TDS increased while pH decreased. Fig. [B] should show these changes in the actual dashboard and record the observed marker color. Across the run, the local database ended with 549 synced and zero pending rows.
